# Comparison acceptance checks

## Intent and evidence

BaudTide is a Linux-first, local serial workbench for board bring-up and repeated bench tests. Main at `4f91477` already compares two saved captures against independently chosen time-zero events, using exact full-interval minimum, maximum, sample mean, and population standard deviation; charts use a bounded overview. It shows candidate-minus-baseline and percent change, but deliberately does not judge whether a change is acceptable. Users repeating a firmware test must currently remember the limits and interpret and transcribe results themselves.

Add optional, user-defined acceptance checks to the existing **Compare test runs** surface. The value is a repeatable, visible decision grounded in the same readings, without inventing what's “better.” This is a recommendation based on the repository, not a claim about measured user demand. No usage or customer evidence was available.

## Approaches considered

1. **Recommended: checks alongside one existing comparison.** Reuse the existing signal pair, interval, full-history statistics, workspace persistence, and CSV summary. Supports a bounded, legible first version and explicit results.
2. A reusable multi-signal bench test suite, automatically run against captures. More expressive, but introduces a new test/run/result model and substantially more UI and persistence. Defer until the single-comparison workflow proves useful.
3. Richer charts and statistics without checks. Improves exploration, but still leaves the repeated acceptance decision and recording of limits to the user.

## Scope and behavior

- A comparison may have zero to eight checks. Each check defines one metric (`min`, `max`, `mean`, or `deviation`), one measure (candidate value, signed candidate-minus-baseline difference, or signed percent change), one inclusive operator (`≤` or `≥`), and a finite numeric limit. No checks are preconfigured. Checks are combined with AND.
- Difference means candidate minus baseline. Percent means `(candidate - baseline) / abs(baseline) * 100`, as in the existing comparison. If baseline is zero, a percent check is **Inconclusive**, not zero or infinity. All calculations use unrounded values; UI and CSV use enough precision to avoid presenting a value apparently on the other side of its limit.
- Example: baseline mean 20 °C, candidate mean 24 °C: candidate mean ≤ 25 °C passes; mean change ≤ 10% fails with observed +20%. The tool describes the configured outcome; it makes no claim that a higher or lower value is inherently better.
- Each check shows its metric, measure, operator, threshold and unit, observed value, and **Pass**, **Fail**, or **Inconclusive** with a reason. The overall outcome is Fail if any check fails, otherwise Inconclusive if any is inconclusive, otherwise Pass. No checks means **No checks configured**, never Pass.
- A completed comparison is the source of truth. Its full-history statistics, not chart points, feed checks. A check is inconclusive if its required value or calculation is non-finite or unavailable. All checks are inconclusive when either side has no matching samples, skipped readings with different units, approximate timing, a known reconnect gap in the requested interval, a capture reports any discarded overlong lines, a capture state is not `saved` or `disconnected`, or an interval clipped by the selected or indexed capture range. Explain which side and why, while leaving the existing statistics and chart available. Unknown data loss cannot be detected reliably; describe a pass as applying to recorded data only, not as proof of a complete or valid hardware test.
- The requested interval is `[anchor + startSeconds, anchor + endSeconds]`, inclusive like the current index. It is clipped when either endpoint lies outside the intersection of `source.selection` and `source.index.range`; an empty or reversed intersection is clipped. A known gap is a `source.gaps` timestamp inside that requested interval inclusive. An invalid gap timestamp makes the result inconclusive. The indexed range is bounded by the first and last accepted telemetry readings, not the physical capture start and end; even a short tail after the final reading makes a check inconclusive. Explain the affected boundary and offer to shorten the interval or record longer. The current replay path may have no reconnect gaps even when a real discontinuity occurred; never present an empty gap list as proof of continuity. The overlong-line count has no interval timestamps, so any nonzero count makes all checks inconclusive for the whole capture. Captures in `capturing`, `error`, `quota-reached`, `interrupted`, or `unknown` state are inconclusive with a state-specific explanation. When an active capture stops, its old index cannot become eligible merely because the state changed: reload/reindex the final capture and rerun comparison. One reading is allowed; its population deviation is zero, and count remains visible.
- The check set is bound to the baseline field key, candidate field key, and exact compatible unit string (empty means unspecified). Capture replacement is allowed when those bindings match. If a field or unit changes, or cannot yet be resolved on restoration, preserve the checks but suspend evaluation with a clear reason. The user can explicitly rebind all checks to the new resolved pair or remove/edit them; never silently reinterpret or discard limits. A rebind requires two valid compatible fields and is a user action, never automatic. When units differ from the previous binding, the confirmation shows both units and states that limits remain numerically unchanged and no conversion is performed.
- Editing, adding, or deleting checks uses a local draft; a valid Save applies it and Cancel discards it. Invalid or unsaved drafts block workspace Save/Update and CSV export until saved or cancelled, with visible guidance. Once saved, checks may be re-evaluated against the same completed comparison without rereading captures. Changing a capture, field, event, selected range, interval or decoder invalidates the measurement and its displayed/exportable verdict until a fresh comparison completes. Cancelled, failed, superseded or closed comparisons never publish stale outcomes.
- Checks and binding persist only when the user saves/updates an existing analysis workspace, alongside existing comparison settings. They are restored as configuration, not as an old verdict; a comparison must be run again. No automatic device writes, background execution, network calls or modification of raw captures. Previous workspaces and comparisons without checks continue to load. Malformed new check data must not make an otherwise valid existing workspace disappear; discard the invalid optional check set, preserving the rest of the workspace, and surface a recovery notice when the workspace is restored.
- Extend the existing comparison CSV summary, only when checks exist, with per-check outcome, observed value, operator, threshold, unit and reason, overall outcome, and enough provenance to interpret it: source names, fields, units, anchor timestamps, requested and effective ranges, capture states, timing modes, sample counts, and skipped-unit counts. Preserve existing summary rows and the existing safe, cancellable desktop export stream. Export must use the same completed snapshot and evaluation as the UI; disable it for stale results, incomplete edits, or running operations. Escape CSV correctly, including quotes and line breaks. Neutralize spreadsheet formula prefixes in user-controlled text cells (including leading whitespace before `=`, `+`, `-`, or `@`, or a leading tab/CR); keep numeric values numeric and document the text escaping. A dialog cancellation or failed write leaves existing files and raw captures unchanged.

Offer **Use overlapping recorded interval** when an interval is clipped: intersect both sources’ selected/indexed ranges after subtracting each source’s own anchor, then set the common start and end (in seconds, preserving millisecond precision). The user must run Compare again. If the overlap has no positive duration, disable the action and explain that different captures, ranges or alignment are needed.

## Visual and interaction design

Keep this inside the existing comparison, below its statistics and above the chart, with an **Acceptance checks** heading, a quiet **Add check** action, and a single ruled list. An empty state explains that checks are optional. A compact inline editor uses existing themed controls: Metric, Measure, Limit type, Limit, Save and Cancel; show the relevant signal unit or `%` adjacent to the limit. At eight checks, explain the limit and disable Add. Each saved row exposes Edit and Remove and reads as a complete sentence, for example “Mean · change ≤ 10%” with “Observed +20% · Fail.” Show the combined outcome close to the heading, but never at the expense of the numeric evidence.

Follow `docs/design.md`: a flat, instrument-like surface, existing tokens and 4-point spacing, Ubuntu Sans for labels and Ubuntu Mono/tabular numbers for measurements, aqua sparingly for action/selection, amber for inconclusive and fault red for failure. Include text and icons, never color alone. Preserve the source panel, statistics, and chart as the dominant workflow; do not introduce a dashboard or unrelated screen. Support Dark, Light, and Sage; use high-contrast focus outlines. At widths under 700px stack controls; at 480px and below use at least 44px controls and 16px inputs, wrap long signal/unit names, and keep the page free of horizontal overflow down to 320px. Any wide data table scrolls only inside its own labelled, focusable region. Honor reduced-motion settings.

Keyboard users can add, edit, save, cancel, rebind, and remove checks; controls have distinct accessible names and associated error text. Announce operation outcomes without repeated live-region noise, keep focus predictable after adding/removing/cancelling, and provide visible hover, focus, disabled, validation, working, empty, failure, and inconclusive states. Avoid nested forms in the existing comparison form.

## Out of scope

Multi-signal suites, automated bench runs or device commands, thresholds inferred by BaudTide, alerting, sharing, additional export formats, unit conversion, and a historical test-results database. Existing live watches remain independent.

## Acceptance and verification

The release gate is a repeatable end-to-end desktop/PTY scenario with two real saved captures and known values, including an aligned interval, checks that pass and fail, saving/restoring an analysis, and inspecting the exported CSV. Use focused domain, persistence, component and export tests for inclusive bounds, negative/zero baselines, full versus decimated data, missing/invalid data, bindings, stale/cancelled work and file safety. Run the repository's `npm test` and `npm run check`. Manually inspect populated, empty, editing, invalid, pass, fail, inconclusive, loading and error states in all three themes at desktop and narrow sizes, with keyboard and reduced motion. Compare screenshots to `docs/design.md`; fix visible clipping, contrast and alignment issues before calling the work done. This plan does not claim hardware validation or visual approval has already occurred.
